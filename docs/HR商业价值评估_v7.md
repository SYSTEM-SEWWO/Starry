# HR 商业价值评估 · 星语 Starry v7.0（第五轮评审）

> 评估人：HRBP（产品商业化顾问视角）
> 评估对象：v7.0 —— 多站点网页接入（智谱清言 / 豆包）/ 选择器覆盖编辑器 / 每日 Token 预算告警 / 并行健康检查 / venv 适配安装 / 三平台 CI
> 评估日期：2026-10-24
> 评估基线：HR 复审 v6.1（GA）后的 V7 候选落地

---

## 一、总体判断

v7 是**「说了就改」信用的 proof of point**：HR 复审 v6.1 遗留的三条观察（O-1 并行健康检查、O-2 选择器覆盖入口、O-3 跨平台 CI）与坦白清单第 3/5 条，**全部闭环，无一条「接受但不改」**。这对商业信任的价值大于任何单项功能——用户和开源社区对「反馈有回音」的敏感度，远高于对功能数量的敏感度。

本轮真正的新增商业价值有两块：

1. **多站点网页接入**——从「DeepSeek 专用马具」升级为「马具工厂」，智谱清言与豆包入场，免费额度用户的覆盖面直接翻倍；
2. **每日 Token 预算告警**——把「 token 烧在哪」从「事后统计」前移为「事中预警」，这是付费 API 用户（商业价值最高的人群）的刚需。

但在完整走查新用户路径后，我发现一个 **P0 级的「货不对板」风险**和两个「文案名不副实」问题。按商业影响排序如下。

---

## 二、问题清单（按优先级）

### P0-1 智谱清言 / 豆包是「未经真机验证」的功能，却被当成熟站点宣传

**现象**：v7 的 README 与设置页把智谱清言、豆包与 DeepSeek 并列呈现为「三个站点」，下拉框里选「智谱清言」→ 登录 → 提问，链路看起来完全就绪。但坦白地说，这两个站点的 9 键选择器是基于公开 DOM 结构的**社区维护推测值**，**从未在真实登录态下跑通过一次提问**。用户如果提问失败，第一反应是「这产品不行」，而不是「这个社区站点需要调选择器」——我们等于把「实验性功能」包装成了「成熟功能」。

**HR 意见**：这不是代码问题，是**诚信问题**，且恰好踩在 v6 P0-1「货不对板」的同一穴位上。两个都要做：
① README 站点表格与设置页站点下拉中，社区维护站点必须带**醒目的「未经真机验证」标注**（不是藏在括号里的小字）；
② 设置页状态行对社区站点明确给出「失效时用选择器编辑器修复 / 到 GitHub Issues 反馈」的路径。
**验证可以缺，明示不能缺。** 这是 P0：它决定 v7 头号新功能（多站点）是「加分项」还是「减分项」。

### P1-1 「每日 Token 预算」的统计口径没有告诉用户

**现象**：用户设了「DeepSeek 每日 80000 token」，看到红色超支条，自然理解为「我在 DeepSeek 的所有消耗」。但实际口径只是**本助手旁路记录的请求**——用户在 DeepSeek 官网直接用、用别的客户端、用 API 脚本跑的 token，一概不计。更微妙的是：预算统计的是**估算 token**（CJK 1 字 ≈ 1 token），与服务商计费本身就有偏差。一个「预算」功能如果口径不清，用户会拿它做消费决策——**拿不准的数字比没有数字更危险**。

**HR 意见**：详情区预算行必须明示口径：「仅统计本助手的请求 · 本地估算值」。不需要改架构（旁路设计是对的），但**不能让用户误会**。

### P1-2 预算超支之后「然后呢」——用户不知道不会被拦截

**现象**：红色「⛔ 已超每日预算」是一个非常强的视觉信号。但产品实际行为是**什么都不拦**（旁路设计）。两类误读都在伤害体验：一类用户以为被限流了，panic 去改设置；另一类以为设了预算就有了「保险」，超支有兜底——其实一分钱都不会少扣。**强视觉信号 + 无行为后果 = 误导。**

**HR 意见**：超支/预警文案里补一句「不会拦截对话，仅作提醒」。同时这恰恰说明旁路设计是对的（真要拦截就成了「监控功能搞挂主干」的经典事故），问题只在文案没把设计意图传达出来。

### P2-1 CI 是「一份文件」，不是「跑过的 CI」

**现象**：`.github/workflows/ci.yml` 三平台矩阵写得漂亮，但到 v7 交付为止，**这套 CI 一次都没有真正跑过**（沙箱没有 GitHub 仓库 push 环境）。Windows 的 pyflakes 输出编码、macOS 的 offscreen 自测、playwright 在 GH runner 上的下载——任何一个小环境差异都会让首次运行翻车。把「未验证的 CI」和「已验证的自测」并列放在 README 里，有暗示前者已达后者的质量之嫌。

**HR 意见**：README 与 CHANGELOG 标注 CI 状态为「已配置，待首次 push 后验证」；坦白清单如实记录。CI 本身方向完全正确，这条只要求**状态诚实**。

### P2-2 多站点让设置页与命令面板的复杂度上升

**现象**：设置页网页接入从「一个开关面板」变成「站点下拉 + 9 键选择器编辑器 + 状态行」；命令面板 20 → 22 个。复杂度是真实代价。

**HR 意见**：**可接受，不要求回退**——选择器编辑器是 O-2 的指定交付物，多站点是 v7 头号卖点。唯一要求：社区维护站点的标注必须醒目（同 P0-1），别让用户在下拉框里「盲选」一个未验证站点。

## 三、HR 特别欣赏的部分（保留）

- **O-1 / O-2 / O-3 三条遗留观察全部闭环**：「并行健康检查 76s → 12s」「选择器逃生舱从 config.json 升级为产品内 GUI」「三平台 CI」——复审时提的每一条都有回音，这是第六轮评审可以持续信任的基础；
- **预算告警的旁路设计**：只统计、不拦截，继承了网关统计的架构品味，从根上避免了「监控功能把主干搞挂」；
- **选择器覆盖编辑器的产品化**：把「留给开发者的逃生舱」做成了「普通用户能用的修复工具」——站点改版这个网页 harness 的宿命，从此有了产品内解；
- **529 项自测覆盖全部新功能**：多站点工厂、选择器编辑器全流程、venv 安装三场景都有回归，没有「吹了牛不测牛」。

## 四、结论

| 编号 | 优先级 | 结论 |
| --- | --- | --- |
| P0-1 | P0 | 必须修复：社区站点「未经真机验证」醒目标注 + 反馈路径明示 |
| P1-1 | P1 | 必须修复：预算统计口径（仅本助手 · 本地估算）写入 UI |
| P1-2 | P1 | 必须修复：超支/预警文案补「不拦截，仅提醒」 |
| P2-1 | P2 | 应当修复：CI 状态标注「待首次 push 验证」 |
| P2-2 | P2 | 接受现状：社区标注醒目即可（随 P0-1 一并处理） |

**总体结论：有条件通过。** v7 的功能方向与架构品味都在线，P0-1 是发布前必须处理的诚信问题（工作量小：标注 + 文案），P1 两条是文案级修复。三条处理完即可 GA，无需再等大功能。继续执行「程序员响应 → HR 复审」闭环。
