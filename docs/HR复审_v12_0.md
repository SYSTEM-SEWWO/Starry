# HR 复审 · v12.0.0

**视角**：团队协作、文档可传承性、新人上手成本、工作量与节奏、流程规范化。

---

## 1. 隐性知识显性化（本轮最大收益）

v11.5 及之前，三件关键事都依赖「有人记得怎么做」：

| 事情 | 过去的形态 | v12.0 的形态 |
| --- | --- | --- |
| 判断 APK 到底装了什么 | 人工解包、肉眼看 `assets/chaquopy/` | `python scripts/verify_apk.py --apk <APK> --strict`，21+ 项可复跑 |
| 保证 PC / 安卓核心一致 | 口头约定 + 手动 `diff -q` 后复制 | `python scripts/sync_core.py --check` + CI 门禁 |
| 一个版本打一个完整文件夹 | 手工复制、容易漏 md / 主文件 | `python scripts/make_release.py --version 12.0.0`，自动出 MANIFEST + checksums + 索引 |

**价值**：新人不需要向老人请教「APK 鉴定怎么弄」「core 改了要不要同步」，
照 README 与 `docs/项目结构与提交指南_v12_0.md` 敲命令即可。
这正是用户长期要求「代码结构方便提交」「像 GitHub 提交项目一样好用」的组织侧落地。

另外，v12.0 把「闪退根因」写成了 `docs/APK鉴定与闪退根因报告_v12_0.md`，
每条 F1–F8 都带文件行号、复现依据、修复位置与对应用例。
**事后复盘变成可检索资产**，而不是聊天记录里的一段结论。

## 3. 新人上手成本

| 环节 | 上手路径 |
| --- | --- |
| 看懂当前版本 | `README.md` 首屏即为 v12.0.0 导航与快速开始，下半部分是 v7 → v11.5 历史编年史 |
| 跑起来 | `pip install -r requirements.txt && python main.py`（桌面）/ `python starry_cli.py --doctor`（CLI）/ `sudo dpkg -i *.deb && starry --version`（Linux） |
| 调新功能 | `API开放文档_v12_0.md` 逐项列出 `core.stardust` 6 个函数、CLI 5 个参数、5 个命令面板 id，含最小完整示例，无需通读实现 |
| 排查安卓 | 「诊断」页直接显示版本 / 平台 / 配置目录 / 异常条数；`starry-crash.log` 可复制反馈，**不再需要 adb** |
| 发版 | 推 `v12.0.0` tag → `release.yml` 自动门禁 → 快照 → Release；或本地一条 `make_release.py` |
| 校验产物 | `check_core_parity.py` / `verify_apk.py` / EXE 冒烟 / deb 独立解析，命令都在文档里 |

安卓端「诊断」页是本轮对**支持成本**的直接改善：过去用户说「闪退」，
开发要问型号、要 adb logcat；现在用户直接把页面上的信息复制过来。

## 4. 工作量与节奏

本轮同时推进且全部收口：

- **鉴定**：真实 51MB 签名 APK 静态解包 + `verify_apk.py` 编写与 3 次自纠；
- **修复**：F1–F8 八项应用级缺陷 + 构建链依赖混装，落在 `core/config.py`、
  `core/__init__.py`、`android/starryandroid/app.py`、`__main__.py`、`pyproject.toml`；
- **测试**：新增 `tests/test_android_v12.py`（37 项）、`tests/test_v12_features.py`（63 项），
  修正旧 fake 测试（16 项），`selftest.py` 4 处硬编码版本改动态；
- **新功能**：`core/stardust.py` 纯逻辑层 + CLI 5 参数 + 桌面 5 条命令 + 安卓自动附卡；
- **工程化**：`sync_core` / `check_core_parity` / `verify_apk` / `build_deb` / `make_release`
  五个脚本，新增 `release.yml`、改造 `build-android.yml` / `build-windows.yml`；
- **产物**：EXE、deb 本机真实构建并冒烟；v11.5.0 历史快照完整保留；
- **文档**：12 份 v12.0 文档矩阵 + README / CHANGELOG / RELEASES 索引。

属于一次完整大版本，节奏与 v11.3 / v11.4 / v11.5 相当，**未堆积半成品功能**；
未完成项（真机验证、v12.0 签名 APK 二进制）都明确标注原因与产出路径，
不是「悄悄略过」。

收尾阶段又追加一轮：Chromium 内核到位后重跑全量自测，**证伪了此前
「12 项失败属环境依赖」的结论**，定位到网关数据目录隔离缺陷并修复为 779/0，
同步更正了发布说明、评审纪要、结构指南等多份文档的口径。
把已经写进交付物的错误判断改对，比维护一个好看的绿色结论更费事，
但对后续接手者的可信度更重要。

## 5. 诚实性作为协作资产

`RELEASE_NOTES_v12_0.md` 第六节「已知限制」明确写了四条不能承诺的事：
本机不能重新签名 APK、无真机不能声称不闪退、deb 形态变化、演示 keystore 风险。
`APK鉴定报告` 也刻意避免把 toga 混装过度归因为「后端选错导致闪退」。

对团队来说，这比一份全是绿色的报告更有价值：**下游知道该去补什么、不该信什么**。
建议在评审模板里固化「验证边界」一节。

## 6. 建议

| 建议 | 理由 |
| --- | --- |
| 安排一次真机 / 模拟器验收排期 | 静态鉴定与本机集成测试无法替代真机 UI 渲染，这是当前唯一的高优先级外部依赖 |
| 建立 keystore 轮换与 Secret 登记流程 | 历史 v11.5 快照仍含演示私钥，公开分发前必须处理 |
| 把 `gh release view` 发布后校验加入 release.yml | 目前靠 artifact 上传成功推断发布成功 |
| 给 `docs/` 加一个按版本的总索引 | 已有 `RELEASES.md`，但 docs 内部已积累 100+ 份历史文档，检索成本在上升 |
