`core/stardust.py`（新）、`core/config.py`（`is_android` / `_safe_makedirs` / `get_config_dir` / `AppConfig.load` 重写）、

## 1. 本轮发现并修复的真实缺陷（发版阻断级）

### 1.1 发布快照可能泄漏任意名称的私钥 —— 已修复

`scripts/make_release.py` 修复前：

```python
EXCLUDE_NAMES = { ..., "starry-release.keystore", "*.keystore", ".env", ... }
def _skip(path, name, size):
    if name in EXCLUDE_NAMES or ...:      # 集合是精确字符串匹配
```

`"*.keystore"` 是**字面量**，任何真实文件名都不会等于它，该规则永不生效；
`shutil.copytree(ignore_patterns(...))` 里也只列了 `starry-release.keystore`
这一个固定名。结论：除那个固定名之外，`my-release.keystore`、`debug.keystore`、
`upload.p12`、`cert.pem` 等会被原样打进 `releases/星语Starry-v12.0.0.zip`
并随 GitHub Release 公开。这与 v11.5 遗留风险表里「演示 keystore 曾随源码分发」
是同一类问题，属于**发版阻断级**。

修复为三层：

| 层 | 位置 | 做法 |
| --- | --- | --- |
| 根级文件 | `_skip()` | 新增 `is_sensitive()`，用 `fnmatch` 匹配 `EXCLUDE_PATTERNS`（修复前为 `False`） |
| 目录复制 | `ignore_patterns(...)` | 增加 `*.keystore / *.jks / *.p12 / *.pfx / *.pem / *.key / *.bak / .env` |
| 发布前 | `assert_no_secrets(dest)` | 复制完成后再遍历快照，命中任何敏感文件立即 `SystemExit` 中止发版 |

设计意图：白名单是「防呆」，扫描是「验证」，两层都要有，规则以后改漏也不会出事。

**实测**：

```
my-release.keystore  is_sensitive=True      README.md  is_sensitive=False
debug.keystore       is_sensitive=True      app.py     is_sensitive=False
upload.p12 / cert.pem / id_rsa.key / config.json / .env / old.bak  → True
空快照 leaks = [] ；含 secret.keystore 的快照 leaks = ['secret.keystore']
```

### 1.2 历史快照内仍有演示私钥 —— 已标注，未擅自删除

全项目扫描命中一处：

```
releases/星语Starry-v11.5.0/android/starry-release.keystore
```

它来自按用户要求「之前的大版本更新也要保留」而完整复制的 v11.5 顶层目录。
**本次不删除、不修改历史快照**（保持历史完整性与可追溯），但必须明确：

- v12.0 快照的 `DIR_WHITELIST` 不含 `releases`，且 `_skip()` 会跳过任何路径中含
  `releases` 段的文件，因此 **v12.0 的文件夹与 zip 不会携带该文件**；
- 若 `releases/星语Starry-v11.5.0/` 曾被或将被上传到公开 GitHub Release，
  **该演示密钥视为已泄漏，必须轮换**；CI 侧已改用仓库 Secret 签名。

## 2. `.starry` 存档的信任边界（避免过高承诺）

`core/stardust.py` 的存档信封是 `magic / version / payload / checksum`，
checksum 为规范化 JSON（`sort_keys=True`、`separators=(",", ":")`）的 SHA-256。

**必须说清楚的定位**：这是**完整性校验**（防传输损坏、误编辑、版本错配），
**不是认证**。攻击者改完 `payload` 后可以自行重算 `checksum` 得到合法信封。
若要防恶意构造，需要 HMAC 或数字签名，而这会引入密钥管理，与本模块
「零依赖、零配置、三端互导」的设计目标冲突。API 文档已按此口径明示，
**不宣称「防篡改」**，只宣称「损坏即拒绝」。

正向安全属性（实测 / AST 确认）：

| 检查 | 结果 |
| --- | --- |
| `unpack_archive` 解析方式 | 仅 `json.loads`；无 `eval` / `exec` / `compile` / `pickle` / `yaml.load` |
| 结构校验 | `magic` 不匹配、`version` 非正整数或大于 `ARCHIVE_VERSION`、`payload` 非 dict、缺 `sessions/memory/meta` 任一字段，全部 `ValueError` |
| 校验失败行为 | 一律抛 `ValueError`，**不返回部分数据**；CLI `--restore` 因此不会写半份数据 |
| 返回值 | 深拷贝，与入参不共享引用 |
| 副作用 | 不读写文件、不访问网络、不解析路径，纯解析函数 |
| 篡改实测 | `tests/test_v12_features.py` 与 `tests/test_android_v12.py` 各有一例改 payload 后导入被拒 |

上层落盘保护：`--restore` 在覆盖前把原文件备份为 `*.bak-<时间戳>`
（实测输出 `原文件已备份 *.bak-20261107-174303`）；`*.bak` 已被发布白名单排除，
不会把用户数据打进 zip。`--archive PATH` / `--restore PATH` 由本地用户显式给定，
不接收远程输入，不存在服务端路径穿越面。

## 3. 配置层：把「崩溃」换成「降级」的代价

- `is_android()` 只读 `sys.getandroidapilevel` 与 `ANDROID_ROOT` / `ANDROID_DATA`
  环境变量，不执行外部命令、不读文件内容，无注入面。
- `_safe_makedirs(path)` 三级回退：目标路径 → `tempfile.gettempdir()/APP_ID`
  → `./.starry-data/APP_ID`，每级 `try` + `os.access(W_OK)` 校验，**绝不向上抛 OSError**。
- `get_config_dir()` 在 Android 上按 `STARRY_CONFIG_DIR`（Toga `app.paths.config` 注入）
  → `HOME/.config` → tempdir 依次降级；桌面仍走 `APPDATA` / `XDG_CONFIG_HOME` / macOS 路径。
- `AppConfig.load()` 的 `except Exception: pass` 是**有意的降级契约**（F1 闪退根因），
  但它会静默吞掉 JSON 损坏、权限错误、编码错误 → 用户可能在不知情下以默认配置
  启动，表现为「API Key 好像丢了」。v12.0 已用安卓「诊断」页（显示配置目录 +
  异常条数）与 CLI `--doctor`（打印配置路径）补上可观测性；
  **建议下版把异常本身写入诊断日志**，而不是完全丢弃。
- `AppConfig.save()` 沿用 v7.5 起的 `chmod 0o600`（POSIX），配置含 API Key 与许可密钥，
  权限收敛正确；本次未削弱。
- 低风险：`tempfile.gettempdir()/APP_ID` 目录名可预测，多用户共享主机上存在
  symlink 抢占的理论面。单机单用户场景不构成实际风险，建议后续用
  `os.open(..., O_NOFOLLOW | O_CREAT | O_EXCL)` 加固。

### 3.1 新增 `STARRY_DATA_DIR` 的安全边界（收尾复核）

`core/gateway.py` 新增的 `_data_dir()` 是一个**可选**环境变量注入点，
用于让全量自测不再读到真实用户目录里累积的网关统计 / 预算数据。
安全审查：

| 检查 | 结论 |
| --- | --- |
| 默认行为 | 未设置时返回 `~/.starry`，与旧版**逐字一致**；不迁移、不删除、不改写任何现有用户数据 ✅ |
| 输入来源 | 仅本地进程环境变量；不来自网络、不来自 `.starry` 存档、不来自用户输入 ✅ |
| 路径解析 | 只做 `os.path.join`，不 `eval`、不 `expandvars`、不跟随符号链接解析 ✅ |
| 目录创建 | `_data_dir()` 自身不创建目录；写文件仍由 `GatewayStats.save()` / `save_budgets()` 的既有 `try/except` 保护 ✅ |
| 权限 | 未放宽；统计与预算文件不含 API Key（Key 仍在 `config.json`，POSIX `0o600`）✅ |
| 与 `STARRY_CONFIG_DIR` 关系 | 同构但**互不影响**：一个管网关旁路数据，一个管配置；任一方缺失都不波及另一方 ✅ |

`chromium_kernel_available()` 同理：只读文件系统、不执行浏览器、不启动子进程、
不联网；`ui/settings_dialog.py` 仅在用户点击按钮时调用它决定是否跳过重复下载。
两项均为零新增攻击面。

## 4. 安卓启动与崩溃日志

- `startup()` 全程 `try` + 应用内「致命错误页」：消除了「异常冒泡 → Toga → 进程被杀」。
  代价是异常不再直接暴露，因此配套 `self.crash_log`、全局 `sys.excepthook`、
  `starry-crash.log` 与「诊断」页。**净效果是可观测性优于 v11.5**，不是掩盖。
- 崩溃日志可能含文件路径与堆栈；用户复制反馈时需自行脱敏。
  建议下版对 `api_key` / `Authorization` 等字段做掩码。
- 日志只追加、无轮转，长期使用会持续增长（低风险，建议设 1MB 上限）。
- 网络一律在 `loop.run_in_executor` 后台线程，UI 回写走 `call_soon_threadsafe`，
  每个回调单独 `try`——既是稳定性修复，也避免异常携带敏感上下文打到主线程日志。

## 5. 依赖与供应链

| 项 | v11.5 实测 | v12.0 处理 |
| --- | --- | --- |
| `toga` 元包 | 裸 `"toga"` 被 Chaquopy（`sys.platform=="linux"`）解析为 **0.2.15** | 去掉裸 `toga`，钉死 `toga-core==0.5.7` / `toga-android==0.5.7` |
| 连带后端 | `toga-gtk 0.2.15` 被打进 Android 包 | 不再解析该元包，产物可复现 |
| 其余依赖 | 未锁版本 | `requests==2.32.3` / `markdown==3.7` / `beautifulsoup4==4.12.3`，`requires-python >= 3.11` |
| 门禁 | 无 | `verify_apk.py --strict` 校验 v1/v2/v3 签名、APK Signing Block 长度自洽、`build.json` SHA1、`.pyc` magic、toga 主版本一致、应用版本、INTERNET 权限；任何 FAIL 阻断 Release |

- `core/stardust.py` 仅 `hashlib / json / re`，供应链面为零。
- `.github/workflows/release.yml` 权限为 `contents: write`（最小集），
  只用 `GITHUB_TOKEN`，**未引入新增长期凭据**；签名密钥改由仓库 Secret 提供。
- `release.yml` 安装依赖全部钉版本，避免 CI 侧漂移。

**边界提醒**：`verify_apk.py` 是**静态结构鉴定**，不执行 APK、不验证证书链可信度、
不替代 `apksigner verify` 与真机安装测试；CI 中两者并用。

| 风险 | 等级 | 建议 |
| --- | --- | --- |
| 历史 v11.5 快照含演示 keystore | 中 | 若曾公开分发则轮换密钥；保留历史文件但不要上传该 zip |

## 结论

**通过（含 1 项发版阻断级缺陷在评估过程中被实证发现并修复）**。

v12.0 新增业务逻辑为纯标准库、无动态执行、无新增网络面；`.starry` 存档的
完整性校验定位准确且未过度承诺安全等级；安卓端「永不抛出」的降级设计配了
诊断与日志，可观测性不降反升；发布链路从「精确名单」升级为
**「通配排除 + 发布前验证」双层门禁**。剩余均为已明示的低 / 中风险改进项，
不阻塞 v12.0.0 发布。
