# 代码安全性评估 · v13.0.0

**评估范围**：`core/project.py`、`core/parallel.py`、`core/updatecheck.py`、
`core/cli.py` v13 分支、`ui/workbench_dialog.py`、`scripts/gen_update_manifest.py`、
`.github/workflows/update-manifest.yml`　**结论：无高危，可发布**

---

## 1. 威胁模型与边界

v13 新增的三层逻辑都在**本地执行**，不引入常驻服务、不开放端口、不写系统目录。
唯一新增的外部输入是 `update.json`（本地文件或只读 HTTP GET）与 `.starryproj`（本地文件）。
因此重点评估「文件内容被篡改」与「联网读取」两条路径。

## 2. 逐项核查

| # | 项 | 结论 | 证据 / 约束 |
| --- | --- | --- | --- |
| S1 | `update.json` digest | **完整性校验，不是签名认证** | `manifest_digest()` 对不含 digest 的规范化 JSON 算 SHA-256。攻击者若能替换清单文件本身，也能重算 digest。已在模块 docstring、CLI 输出、API 文档、发布说明四处显式标注；生产环境建议再加签名验证 |
| S2 | 资产 SHA-256 | 通过 | `verify_asset_sha256()` 分块读取（64 KiB）比对，非法期望值 / 文件缺失一律返回 False 不抛；下载与替换**不由本工具执行**，只给结论 |
| S3 | 远程清单读取 | 低风险 | `_fetch_manifest()` 用标准库 `urllib.request` 只读 GET，`timeout=6`，读取上限 1 MiB，失败打印后返回 None；不写文件、不跟随到任意协议（校验 URL 以 http/https 开头由 `validate_manifest` 保证） |
| S4 | 清单结构校验 | 通过 | `validate_manifest()` 严格检查 magic / schema / app_version / digest / assets 非空 / platform 白名单 / name / URL scheme / 64 位 hex / size 非负整数；任一不符即收敛为「不可判定」，不抛异常 |
| S5 | `.starryproj` 反序列化 | 通过 | 使用 `json.loads`（不执行代码）；校验 magic、版本上限、tasks 必须为 list、checksum；任一失败抛 `ValueError` 并由调用方拒绝载入。`unpack_project` 对非 dict 根节点显式拒绝 |
| S6 | 并行执行器 | 通过 | `local_worker` 不做文件写入、不执行命令、不 eval；`check` 任务只读 `os.path.exists`。`chat` 任务默认明确报错，只有显式 `--execute` 才构造真实客户端 |
| S7 | 单线异常隔离 | 通过 | 每个 job 在 `_call()` 内独立 try，异常转成 `{ok:False,error}`，不扩散到其它线；`fut.result()` 外层再兜一层 |
| S8 | 超时 / 资源耗尽 | 通过 | `as_completed(timeout=...)` + `ex.shutdown(wait=False, cancel_futures=True)`，超时不等待残留线程；`run_project` 有 100 波防御上限，循环依赖收敛为 skipped |
| S9 | 工作台文件操作 | 通过 | 保存/载入/导出全部经 `QFileDialog` 由用户显式选择；写入用 `open(..., encoding="utf-8")` 并捕获 `OSError`；不自动覆写、不自动下载 |
| S10 | 发布快照敏感文件 | 通过 | `make_release.py` 的 `EXCLUDE_PATTERNS`（`*.keystore/jks/p12/pfx/pem/key`、`config.json`、`.env`、`*.bak`）+ `assert_no_secrets(dest)` 发布前中止。v13 新增的 `update.json` 不含任何凭据 |
| S11 | 环境变量 | 通过 | `STARRY_UPDATE_URL` 只读；`STARRY_DATA_DIR` 沿用 v12 契约（仅影响 gateway 数据，不改变默认 `get_config_dir()` 行为） |
| S12 | CI 权限 | 通过 | `update-manifest.yml` 声明 `permissions: contents: write`，仅用于 `gh release upload`；`GH_TOKEN` 用 `${{ github.token }}`，不引入第三方 secret |

## 3. 风险定级

| 级别 | 数量 | 说明 |
| --- | --- | --- |
| 高 | 0 | — |
| 中 | 1 | S1：清单完整性 ≠ 认证。**已缓解**：只接受可信来源、不自动下载/替换、四处文档显式警示 |
| 低 | 2 | 本地离线清单含项目既有占位仓库 URL（notes 已标注）；`--update-url` 在离线环境会等待最多 6s |

## 4. 与 v12 的增量

v12 修掉了 `make_release.py` 的密钥通配排除缺陷与 selftest 数据隔离问题。v13 **未削弱**任何既有边界：
`STARRY_DATA_DIR` 契约保留、`assert_no_secrets()` 保留、`.starry` 存档校验保留。
新增的 `.starryproj` 采用同款「magic / version / payload / checksum」信封，安全语义一致。

## 5. 结论

**通过**。新增代码没有引入网络服务、动态代码执行、凭据写入或自动替换程序的能力。
唯一需要使用者知晓的是：自动更新只做完整性判定，不替代供应链签名验证。
