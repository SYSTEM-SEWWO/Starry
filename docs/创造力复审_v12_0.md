# 创造力复审 · v12.0.0

**视角**：是否真的「多想了一步」，而非机械堆功能；是否把不可能变成可交付。

---

## 1. 把「闪退」从猜谜变成取证

前几轮面对「APK 装了就闪退」的做法是：改 `app.py` → 再改 `app.py` → 再改一次。
v12.0 换了一个问题：**「先别猜，打进 APK 的到底是什么？」**

于是有了 `scripts/verify_apk.py`——不是又一份检查清单，而是把 APK 当成
证据来读：

```
ZIP → AndroidManifest / resources.arsc / classes.dex
    → v1 META-INF/*.SF + v2/v3 APK Signing Block（头尾长度自洽）
    → assets/chaquopy/app.imy（ZIP of .pyc）对 build.json 的 SHA1
    → .pyc magic 对应 CPython 3.11
    → requirements-common.imy 里的 dist-info 依赖版本
    → AXML UTF-16LE 字符串池里找 INTERNET 权限
```

这一步的创造性不在技术难度，而在**换问题**：从「我改哪行能不崩」
换成「这个包到底是不是我以为的那个包」。结果直接挖出了
`toga 0.2.15 / toga-core 0.5.7` 两代混装这个此前完全没人怀疑的变量。

更难得的是**工具自身也被质疑了三次**：Signing Block 长度解析写错、
应用 `dist-info` 其实在 `app.imy` 内而非 `requirements-common.imy`、
AXML 字符串池是 UTF-16LE 导致权限漏报——三次都先修工具再下结论，
没有把「鉴定器的误报」当成「产品的缺陷」。

## 2. 最反直觉的发现：测试全绿正是 bug 的帮凶

「16/16 通过」通常是最令人安心的一句话。本轮却定位到：
旧 fake 是**照着被测代码写的**——`FakeMemory` 复刻了错误的关键字参数，
`FakeWidget` 自带真实 Toga 根本不存在的 `scroll_to_bottom()`，
`Selection` 不校验 `value`。于是三个真机必崩的缺陷在测试里全被抹平。

由此提炼出一条可复用的原则，并直接改写了测试架构：

> **替身必须忠实于真实依赖的行为，而不是忠实于被测代码。**
> 否则测试只能证明「代码和自己一致」。

`tests/test_android_v12.py` 因此用**真实 `core`**，fake 只做 UI，
并且故意让 fake `Selection` 在值不合法时抛 `ValueError`、
故意**不提供** `scroll_to_bottom()`、故意让 `App.loop` 保持只读。
还专门写了一条用例证明「旧的错误调用确实会失败」——把历史 bug
变成永久的回归证据，而不是修完就忘。

这比补五十个用例更有设计感：**修的是判断力，不是覆盖率数字。**

## 3. 把「过程」变成「可带走的产物」

`✦ 星尘卡` 是本轮最能体现产品想象力的一个功能：

- 用户在界面上看到的「深度思考」是**流式过程**，关掉窗口就没了；
- v12.0 用 `build_echo_card` 把思考起点、思考落点、回答摘录、
  分片数、token 量级、分支锚点收成一张 Markdown 小卡；
- **零 token、零联网、不调模型**——它不花用户一分钱，也不依赖服务可用；
- 纯文本，能复制进任何笔记软件，桌面 / CLI / 安卓三端同一份排版。

「不调用 AI 来提供 AI 产品的价值」是一个很漂亮的反向思路：
模型负责回答，**本地确定性代码负责让回答变得可留存**。

## 4. 两个「先看再做」的克制设计

| 设计 | 常规做法 | v12.0 的做法 | 好处 |
| --- | --- | --- | --- |
| 上下文预算 | 超预算直接丢掉旧消息 | `plan_trim` 只返回 `keep_indices / drop_indices` 计划 | 用户先看到「准备丢第 1、3 条」再决定，纯函数层完全不碰状态 |
| 存档导入 | 读进来就覆盖 | `unpack_archive` 四重校验全过才返回；`--restore` 覆盖前先备份 `*.bak-<时间戳>` | 损坏文件不会写半份数据，误操作可回退 |

克制比堆功能难。这两个接口都刻意**把决定权留给调用方 / 用户**，
而不是替用户把事做完。

`.starry` 信封另一处巧思：checksum 对
`sort_keys=True + separators=(",", ":")` 的规范化 JSON 计算。
若直接哈希普通 `json.dumps`，三端键顺序不同就会互相拒绝导入——
**把跨端一致性做进格式本身**，而不是写进文档靠人遵守。

## 5. 流程性创造力：把用户的一句抱怨变成一条流水线

用户说「每更新一个版本，把所有更新的东西放到一个带版本后缀的文件夹」
「要像 GitHub 提交项目和 Releases 一样好用」。这两句本来可以被理解成
「这次手工整理一下」，本轮把它做成了机制：

```
make_release.py  →  一个版本 = 完整自包含文件夹 + 同名 zip
                    + MANIFEST.md（逐文件 SHA-256）
                    + checksums.txt + RELEASES.md 倒序索引
release.yml      →  tag → 门禁 → 全量自测 → 快照 → Release 正文/资产
sync_core.py     →  「记得手工 diff」变成 `--check` 一条命令
verify_apk.py    →  「肉眼看 APK」变成 CI 阻断门禁
```

**下一次发版不再需要人记得任何步骤。** 把教训与要求固化成可执行流程，
比这一次做对更有长期价值——延续了 v11.5「把事故写进流程」的思路，
但这一步覆盖的是整个交付链。

## 6. 把「诚实」也当成设计约束

在没有 JDK / Android SDK / Gradle / `apksigner` 的 Windows 机器上，
最容易的做法是替换 `app.imy` 后交一个「v12.0 APK」——
但那会让 v1 摘要与 v2/v3 签名全部失效，是个装不上的包。

本轮选择：**不伪造二进制**，明写「源码已修复、签名 APK 由 CI 在 tag 时真实产出」，
并给出 `verify_apk.py --strict` 作为到货验收手段；报告里也不把
toga 混装过度归因成「后端选错导致闪退」，只说它是「构建链高危变量」。

对一份工程交付来说，清楚标注「验证了什么 / 没验证什么」
和「能做什么」同样重要。这也是一种设计判断。

收尾时还做了一次**自我证伪**：此前把 `selftest.py` 的 12 项失败归因为
「环境依赖，CI 干净环境能过」，Chromium 装好后失败依旧。没有继续找新借口，
而是逐层加隔离变量把失败数从 12 → 5 → 0，最终定位到
`~/.starry` 在 Windows 上读 `USERPROFILE` 这一平台语义差异，
并给生产代码补了默认行为不变的显式注入契约。
承认自己上一轮判断错了、再去改已经发出的发布说明，
比维护一个漂亮的绿色结论更费事，也更值得。

## 7. 仍可更大胆的方向（供下一版参考）

- **星尘卡时间线**：把多轮卡片按 `branched_from` 串成可回溯的思考地图，
  点击任一卡片回到当时的分支点。
- **上下文预算可视化**：把 `plan_trim` 的下标计划画成一条可拖拽的时间轴，
  用户手动调整保留区间后重新生成计划。
- **存档增量与跨设备同步**：当前是全量信封，可做差分 + 可选端到端加密
  （顺便把 checksum 升级为 HMAC，补上认证能力）。
- **真机自动化矩阵**：把 37 项集成回归搬到设备农场，配合启动耗时 /
  内存曲线，让「不闪退」第一次拥有真机证据。
- **APK 差异鉴定**：`verify_apk.py` 支持对比两个版本的 `app.imy`，
  自动列出「本次究竟改了哪些模块」，直接生成 Release 变更清单。

---

## 结论

**通过，且是近几个版本里思维跨度最大的一次**。
本轮既有方法上的转向（猜测 → 取证）、测试观上的纠偏（假绿 → 忠实替身），
也有产品上的巧思（零 token 的星尘卡、先看再做的裁剪计划），
更把用户的交付要求固化为 `make_release.py` + `release.yml` 的可重复流水线。
符合「深度思考多一点、创造力」的要求。
