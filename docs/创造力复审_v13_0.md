# 创造力复审 / 创造力评价 · v13.0.0

**视角**：原创性、组合价值、克制度、可延展性　**结论：通过，创造力评价 A-**

---

## 1. 本版四项原创组合

### 1.1 「整体项目」作为一等公民，而不是并行的附属参数

用户说「多线并行前面加一个整体项目」。最容易的做法是给并行函数加个 `project_name` 参数；
本版选择把项目建模成**带状态机、依赖图、产物与存档的独立实体**（`core/project.py`），
并行执行器只是它的一种调度方式。于是用户面对的是「一个项目跑完了没有」，
而不是一堆散落的线程结果。这个抽象层级的抬升，是 v13 最有价值的一步。

### 1.2 默认模板即「可运行的教学样例」

`plan_from_goal()` 生成的不是空项目，而是「三条并行 + 一条依赖汇总」的最小完整拓扑。
用户第一次运行 `--parallel` 就能看到：第一波 3 条同时完成、第二波 1 条汇总、进度到 100%。
**用产品自身的默认行为演示产品的核心概念**，比写三页说明更有效。

### 1.3 可移植的「项目」`.starryproj`

v12 的 `.starry` 存档搬的是会话与记忆；v13 的 `.starryproj` 搬的是**未完成的思考结构**：
目标、任务、依赖、状态、结果都可以序列化、校验、再载入继续执行。
同款「magic / version / payload / checksum」信封让两个格式的安全语义一致，
但语义对象完全不同——这是对既有设计的正确复用，而不是复制粘贴。

### 1.4 文本版工作台 `--workbench`

把 GUI 工作台的能力压缩成一条命令行：环境 + 项目 + 并行 + 更新 + 命令速查五段 Markdown，
**完全离线可跑**。这让「复刻 WorkBuddy」不只是一块界面，而是任何终端、CI、SSH 会话里
都能调用的能力；也让 EXE 冒烟可以断言「项目进度 100%」这种真实业务结果，
而不只是「进程没崩」。

## 2. 克制度评价（同样重要）

创造力不等于堆功能。本版主动**克制**了三件事：

| 没做 | 为什么 |
| --- | --- |
| 自动下载并替换程序 | 更新只做判定，下载与替换交给使用者；避免把「检查更新」变成有写权限的攻击面 |
| 默认调用大模型跑并行线 | 默认 worker 是本地确定性执行，零 token、零联网；`--execute` 才显式启用模型 |
| 伪造一个 v13 APK 或编造资产哈希 | 本机无 Android 工具链就明确写「不含 APK」；生成器发现 README 被当资产立刻自我证伪 |

**「校验全绿但产物是假的」是最需要警惕的失败模式**。本版在这个点上没有妥协，
反而在创造力评价里把它列为加分项——知道自己不该生成什么，比能生成什么更难。

## 3. 可延展性

| 现有基础 | 下一步自然演化 |
| --- | --- |
| `kind=chat` 已预留 | 多模型并行会诊、不同服务商跑同一任务做对比 |
| `depends` 是任务 ID 列表 | 从线性分波升级为 DAG + 关键路径分析 |
| `.starryproj` 可携带 result | 项目模板市场、断点续跑、跨设备接力 |
| `update.json` 平台资产表 | 增量更新 / 差分补丁 / 渠道（stable、beta） |
| 工作台 QSplitter 左右分栏 | 产物预览、时间线视图、任务详情编辑器 |

## 4. 不足

1. 工作台的视觉语言沿用 `InsightDialog`，稳妥但缺乏辨识度；深色主题未适配（见美术复审）。
2. 默认模板是固定三条线，尚未做到「根据目标自动判断该拆几条线」——
   目前是确定性模板，不是智能规划。这是诚实的选择（离线、可测），但也确实是能力上限。
3. 文本工作台在 Windows GBK 终端里 `✦` 会降级为 `?`，观感略损。

## 5. 创造力评价

| 维度 | 评分 | 说明 |
| --- | --- | --- |
| 抽象层级 | A | 把「整体项目」抬成一等实体，而非并行的参数 |
| 组合新颖度 | A- | 项目状态机 × 分波并行 × 可移植存档 × 离线工作台 × 真实哈希清单，组合是新的 |
| 体验巧思 | A | 默认模板自演示、①② 编号引导、文本版工作台 |
| 克制度 | A+ | 拒绝伪造资产、拒绝自动替换、拒绝默认烧 token |
| 视觉原创性 | B | 沿用既有设计体系，稳妥但保守 |

**综合：A-。** 本版不是靠堆砌功能数量取胜，而是靠「把用户一句话里的层级关系
（整体项目在多线并行之前）真正建模出来」，并让这个模型在 CLI、GUI、EXE、deb、
CI 五种形态下都成立。
