# 创造力复审 / 创造力评价 · v13.1.0

## 1. 本轮最有创造力的三个决定

### ① 把「GUI 程序无法自证」变成可自动化验证的落盘自检

用户要的是「GUI 版 EXE」。最省事的做法是打包完双击一下、看到窗口就算完。
但窗口程序 `console=False`、`sys.stdout` 可能为 `None`、CI 没有桌面，
这三件事叠加会让「验证」退化成「构建日志里没有 ERROR」。

v13.1 的做法是给 `main.py` 加 `--selftest --out r.json`：
自检结果**写文件**，由 `scripts/smoke_gui_exe.py` 启子进程、读文件、逐项断言。
更关键的是自检内容包含「随包 `skills/` 已打进产物」——它不是检查
「代码写了吗」，而是检查「这个 EXE 里真的有吗」。

这直接闭合了 v13.0 创造力复审里最担心的一句话：
**「校验全绿但产物是假的」才是最需警惕的失败模式。**

### ② 用「往返一致性」而不是「能解析」来测多生态兼容

兼容 Claude Code / GitHub / WorkBuddy 的 `SKILL.md`，表面工作是把 frontmatter
读出来。但真正会出错的地方在**往返**：本地技能 → 导出 `hub.json` → 再比对，
如果 id 或内容摘要在任一环节被重造，就会「看起来全对、结论全错」。

v13.1 把这条往返做成核心断言：
`check_hub_update(found, build_hub_manifest(found))` 必须是 `update_available=False`。
正是这条测试逼出了 P2（id 加了 `remote:` 前缀）和 P3（用重算 sha256 比对）
两个靠单点冒烟绝对发现不了的缺陷。

### ③ 把路径推断收敛成 core 层的一个函数

`skills/` 在源码运行时位于项目根，在 PyInstaller onefile 里位于 `sys._MEIPASS`，
在 deb 里位于 `/opt/starry/skills`。CLI 和 GUI 若各写一份推断，迟早漂移。
`bundled_skills_dir()` 一处定义，三处形态自动对齐，还顺手让
`default_sources()` 在所有端都有同样的默认技能。

## 2. 克制的地方（同样是创造力）

- **没有引入 PyYAML**。手写极简 frontmatter 解析器，并在 API 文档里明确
  写出「有意限定的子集」与「不支持写法会降级为字符串」。
  用 60 行换三端零依赖，比为通用性引入依赖更合适。
- **没有把 Hub 做成在线商店**。只发现、只比对、不下载、不执行；
  唯一写操作要用户显式点「导入」。这与产品「本地优先」的定位一致。
- **没有把技能更新和程序更新合并**。`update.json` 与 `hub.json` 两条线分开，
  各自有独立的校验与 UI 入口，语义清楚，出问题也容易定位。
- **没有伪造 APK**。本机无签名工具链，`apk/` 目录仍只放 README，
  财务清单里照样单列 APK。

## 3. 诚实度检查

| 容易粉饰的地方 | 本版写法 |

## 4. 评价

**A**（v13.0 为 A-）。

升级理由：v13.0 的创造力主要体现在「功能架构」（整体项目 → 多线并行 → 更新），
v13.1 则把创造力用在**验证架构**上——让一个没有控制台、没有显示器、
没有网络的 GUI EXE 也能被 CI 严格证伪，让多生态兼容的「标识一致性」
成为可复跑的往返测试，而不是靠人眼比对。

这类工作不产生新按钮，但决定了前面所有按钮能不能被信任。

## 5. 下一版可以更大胆的方向

1. Hub 清单的可选 Ed25519 签名，把「完整性」升级为「来源认证」。
2. 技能 → 整体项目任务的映射：把 `SKILL.md` 正文直接作为某个任务的提示词，
   让 Skills Hub 与工作台真正串成一条工作流，而不只是并列的两个窗口。
3. 暗色主题统一供给（`ui/theme.py`），把两个新对话框也纳入。
4. `gh release view` 发布后校验 + 默认分支动态回写，把 GitHub 复审剩余两项关闭。
