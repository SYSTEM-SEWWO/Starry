## 二、Commit Message 规范（Conventional Commits + 中文）

本项目采用 [Conventional Commits](https://www.conventionalcommits.org/) 规范，格式：

```
<类型>(<范围>): <主题>          # 主题 ≤ 50 字，不加句号

<正文>                          # 可选：说明动机、对比行为、副作用
                                 # 每行 ≤ 72 字符

<脚注>                          # 可选：BREAKING CHANGE: / Refs: #issue
```

**允许的类型**：

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat(gateway): 新增密钥池轮询与失败退避冻结` |
| `fix` | 缺陷修复 | `fix(modelscope): 下载前取消不再抛 NameError` |
| `docs` | 文档 | `docs: README 补充网页版接入章节` |
| `style` | 格式（不影响语义） | `style: 统一 import 排序` |
| `refactor` | 重构 | `refactor(ui): 抽取液态玻璃组件库` |
| `perf` | 性能 | `perf(api): 流式解析减少字符串拼接` |
| `test` | 测试 | `test: 新增健康检查进度信号断言` |
| `build` | 构建/打包 | `build: spec 收集 Playwright node driver` |
| `chore` | 杂项 | `chore: 更新 .gitignore` |

**本项目惯用范围（scope）**：`web`（网页版接入）、`gateway`（网关）、`liquid`（液态玻璃）、
`agent`（智能体）、`ui` / `core` / `app`（分层）、`docs`、`build`。

### 本项目提交历史示例（v6 开发过程的标准拆分）

如果要把 v6 的工作按开源惯例拆成多个提交，推荐这样组织（**当前交付为整理后的单次初始提交，见第四节**）：

```bash
git commit -m "feat(web): 新增 DeepSeek 网页版浏览器接入（harness）

- core/browser_llm.py：Playwright 驱动真实 Chromium，线程亲和会话、
  登录态持久化、多重备选选择器、流式增量抓取、随时停止
- core/web_deepseek.py：站点适配器与工厂函数
- 多轮对话经「前情提要」纯文本拼接发送，承认网页版无上下文 API
- 选择器支持 config.json 整体覆盖，站点改版免升级修复"

git commit -m "feat(gateway): 新增网关仪表盘（统计/密钥池/健康检查/路由）

- core/gateway.py：旁路统计（绝不拦截主链路）、Key 轮询与冻结、
  GET /models 探活、auto/fastest/manual 路由策略
- ui/gateway_dialog.py：液态玻璃旗舰界面，指标环/服务商卡片/
  延迟折线/密钥池/日志流，健康检查带实时进度"

git commit -m "feat(liquid): 新增液态玻璃组件库

- ui/liquid.py：LiquidGlass/LiquidCard/GlowOrb/StatusDot/
  MetricRing/Sparkline/NumberRoll，纯 QPainter 自绘
- 四要素：磨砂底 + 顶部高光 + 1px 亮边 + 主题色光晕"

git commit -m "fix(modelscope): 下载前取消不再抛 NameError

should_stop 提前检查引用了尚未定义的 write_path，
现把临时文件路径计算移到检查之前。"

git commit -m "docs: 补齐开源提交规范文件（LICENSE/CHANGELOG/.gitignore/spec）"
```

## 三、Pull Request 描述模板

新建 PR 时把下面内容粘进 PR 正文（仓库 `.github/PULL_REQUEST_TEMPLATE.md` 也可落一份）：

```markdown
## 概述
<!-- 这个 PR 做什么，解决什么问题 -->

## 变更类型
- [ ] feat（新功能）
- [ ] fix（缺陷修复）
- [ ] docs（文档）
- [ ] refactor（重构）
- [ ] test（测试）
- [ ] build（打包）
- [ ] chore（其他）

## 动机与背景
<!-- 为什么需要这个变更；关联 issue 请写 Refs: #123 -->

## 实现要点
<!-- 关键设计决策、权衡、遗留已知边界 -->

## 验证证据
- [ ] `python3 selftest.py` 全绿（463 项）
- [ ] `python3 verify_v6_browser.py` 12/12（涉及网页版时）
- [ ] 真实显示环境冒烟通过（涉及 UI 绘制时）
- [ ] README / CHANGELOG 已同步

## 截图（涉及 UI 时必填）
<!-- before / after 对比图 -->

## 已知边界 / 后续事项
<!-- 坦白清单：这个 PR 没做什么、依赖什么外部条件 -->
```

## 四、当前文件夹的提交方式（拿来即用）

`ai-assistant/` 目录已经处于「干净可提交」状态（无缓存、无运行时数据、
`.gitignore` 已覆盖 `config.json` / `sessions.json` / `gateway_stats.json` /
`.starry/` / `browser/` 等本地产物）。按下面任选其一：

### 方式 A：单次初始提交（推荐，历史干净）

```bash
cd ai-assistant
git init
git add .
git commit -m "feat: 星语 Starry v6.1 —— 本地桌面 AI 助手（网页版接入/网关仪表盘/液态玻璃）

PyQt5 桌面 AI 助手：19 家服务商（含 DeepSeek 网页版浏览器接入）、
四种本地模型、网关仪表盘（密钥轮询/健康检查/路由策略）、液态玻璃
组件库、智能体框架、463 项自测。

详见 README.md 与 CHANGELOG.md。"
git branch -M main
git remote add origin <你的仓库地址>     # 如 https://github.com/<you>/starry.git
git push -u origin main
```

### 方式 B：按第二节的示例拆成多个提交后再推送

先 `git init`，然后按功能模块分批 `git add <路径>` + `git commit`，
最后 `git push`。适合希望展示「演进过程」的评审场景。

### 提交后建议补的三个仓库文件（可选但推荐）

1. `.github/PULL_REQUEST_TEMPLATE.md` —— 落入第三节模板；
2. `.github/ISSUE_TEMPLATE/` —— bug 报告 / 功能建议两个模板；
3. `SECURITY.md` —— 说明「API Key 仅存本地 `config.json`，仓库永不收集」。

## 六、常见提交问题自查

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| push 后被提醒含密钥 | 误提交 `config.json` | `git rm --cached config.json` 后改 `.gitignore`，并**立即轮换该 Key** |
| 打包文件几百 MB | 误提交 `.venv/` 或 `dist/` | 按第五节核对 `.gitignore` |
| 网页版功能在安装包里不可用 | 安装包不含浏览器内核（已知边界） | README「安装包边界」已明示；用户按设置页一键安装 |
| CI 跑 selftest 失败 | CI 无显示器 | 用 `QT_QPA_PLATFORM=offscreen`（README 自测节有命令） |
