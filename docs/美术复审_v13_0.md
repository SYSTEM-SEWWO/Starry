## 1. 评审对象

| 对象 | 形态 |
| --- | --- |

| `core/parallel.py::merge_results` | 并行结果表格 |

## 2. 视觉一致性

工作台沿用 `ui/insight_dialog.py` 的浅色视觉语言，没有另起一套：

| 元素 | 取值 | 一致性 |
| --- | --- | --- |
| 卡片背景 | `#ffffff` / `#fafbfc`，边框 `#e3e8ef`，圆角 10px | 与洞察面板一致 |
| 主色 | `#2563eb`（主按钮 / 进度条 chunk） | 与 v7 起的天蓝体系一致 |
| 正文 | `#0f172a` / `#16293c`，次要 `#64748b` | 与既有 QSS 一致 |
| 按钮 | 次要白底描边 `#cbd5e1`；主要蓝底白字 | 层级明确 |

`_BTN` / `_PRIMARY` / `_TREE` / `_BROWSER` 四组 QSS 收敛在模块顶部常量，
后续换肤只需改一处，符合 v12 建立的可维护性约定。

## 3. 信息层级

```
标题（16px 粗）        ✦ 星语工作台
副标题（11px 灰）      版本 + 「默认离线执行」承诺   ← 先安抚「会不会烧 token」
目标行                 [输入框] [① 规划项目] [② 多线并行执行]  ← 编号引导操作顺序
主体（QSplitter）      左：任务树（4 列）  右：Markdown 报告
进度行                 状态文字 + 220px 进度条
操作栏                 保存 / 载入 / 导出 / 检查更新 ……… 关闭
```

**优点**：①② 的编号把「先规划、再执行」的依赖顺序直接画在界面上，
与 `core.project` 的依赖模型呼应；`run_btn` 在无待办任务时 `setEnabled(False)`，
避免用户反复点击无反馈。

## 4. 状态可读性（双编码，照顾色觉差异）

| 状态 | 符号 | 文字 | 颜色 |
| --- | --- | --- | --- |
| 完成 | ✓ | 完成 | 深绿 |
| 失败 / 跳过 | ✗ / - | 失败 / 跳过 | 红 |
| 执行中 | … | 执行中 | 默认 |
| 待办 | · | 待办 | 默认 |

**不是只靠颜色区分**：符号 + 文字 + 颜色三重编码，符合可访问性要求。
任务树 4 列（任务 / 状态 / 类型 / 依赖）让「为什么这条还没跑」一眼可见——
依赖列直接显示 `t1, t2, t3`，与项目模型的 `depends` 字段对应。

## 5. 文本版工作台的排版

`--workbench` 输出是标准 Markdown 五段（环境 / 整体项目 / 多线并行 / 自动更新 / 常用命令），
段落之间用空行分隔，进度用粗体，任务列表统一采用「状态符号 + 加粗标题 + 状态文本」三段式。
在 Windows 控制台 GBK 环境下中文可正常显示（EXE 子进程实测通过），
符号 `✦` 会降级为 `?`，但这属于终端编码固有限制，不影响信息完整性。

> 说明：EXE 输出中 `✦` 显示为 `?` 是 cp936 编码兜底结果，
> `core.cli._emit()` 的 `errors="replace"` 保证不会因打印而崩溃——这是 v11.5 修过的问题，本版保持。

## 6. 改进建议（不阻塞发布）

1. **暗色主题适配**：工作台目前是硬编码浅色 QSS，与 `InsightDialog` 一致，但也继承了同一局限。
   项目支持 `light / sky / dark / sky_dark` 四主题，工作台尚未跟随 `get_theme()`。
   建议下一版把四组 QSS 常量改为按主题注入，避免深色主题下出现白底刺眼面板。

## 7. 结论

**通过**。新增界面没有破坏既有视觉体系，操作顺序、状态编码、信息密度都经过设计，
且未引入图标/字体等外部资源，EXE 体积不受影响。
