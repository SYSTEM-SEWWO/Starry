## 一、整体项目定义（验收口径）

| 项 | 口径 |
| --- | --- |
| 目标 | 电脑端功能更多的更新：整体项目 + 多线并行 + 自动更新 + WorkBuddy 式工作台 |
| 硬约束 | Windows EXE / Linux deb 开箱可用；默认离线、不要 API Key、不要联网 |
| 交付 | 每个版本一个完整自包含文件夹（全部源码 + 主文件 + 全部 md + 构建脚本 + 资产） |
| 保留 | v11.5.0 / v12.0.0 历史快照不覆盖、不删除 |
| 禁止 | 伪造 APK、编造更新资产哈希、把说明文档写成二进制资产 |
| 门禁 | 版本单一真源 + 三端同源 + 全量 AST + 全部测试 0 失败 + 产物真实可运行 |

## 二、各线结论摘要

| 复审 | 一句话结论 | 关键发现 |
| --- | --- | --- |
| 代码安全性 | 通过，无高危 | 更新清单 digest 是完整性校验而非签名认证，已显式写入文档；`--update-url` 只做只读 GET 且 6s 超时；`.starryproj` checksum 拒绝篡改 |
| HR | 通过 | 三层纯逻辑可被三端复用；「离线开箱可用」把演示/试用门槛降到零；文档矩阵完整，交接成本可控 |
| 美术 | 通过 | 工作台沿用 `InsightDialog` 浅色视觉语言；任务树状态用颜色 + 符号双编码；进度条与状态栏信息密度合理 |
| 资深程序员 | 通过（附 2 条改进） | `ThreadPoolExecutor` 超时用 `shutdown(wait=False, cancel_futures=True)` 避免 CLI 卡死；`run_project` 结果按输入顺序回填。改进 1：生成器不得按目录推断资产类型（已修）；改进 2：测试不得与发版号耦合（已修） |
| GitHub | 通过（附 3 条建议） | 5 个 workflow YAML 合法；新增 `update-manifest.yml` 解决「异步追加资产导致清单不全」；建议发布后跑 `gh release view` 校验、GUI exe 随 tag 进 Release、修正 detached HEAD 下 `HEAD:main` 回写 |
| 创造力 | 通过 | 「整体项目 → 分波并行」模板、`.starryproj` 可移植项目、文本版 `--workbench`、从真实字节生成更新清单，四项均为本版原创组合 |

## 三、反复优化轨迹（缺陷闭环）

| 轮 | 发现 | 处理 | 证据 |
| --- | --- | --- | --- |
| 1 | 三模块落盘后冒烟脚本误用 `run_project` 返回值（实为 tuple） | 读真实实现后修正调用，不靠猜测 | `core/parallel.py:170-208` |
| 2 | `build_manifest(assets=dict)` 被冒烟脚本误传 | 明确 assets 契约为 `list[dict]`，写入 API 文档 | `core/updatecheck.py:82-95` |
| 3 | 损坏 `.starryproj` 载入打印两行重复提示 | `_run_project` 改为失败即返回 | `core/cli.py` |
| 4 | 版本升 13.0.0 后 v13 单测 3 项失效 | 远端版本改 `99.0.0`；v12 测试改动态真源 | `tests/test_v13_features.py` |
| 5 | **生成器把 `apk/README.md` 当成 android 资产** | 改为只按二进制扩展名判定，拒绝空清单 | `scripts/gen_update_manifest.py` + 10 条新单测 |
| 6 | EXE 冒烟断言把 GBK 输出按 UTF-8 解码导致误判 | 冒烟脚本改用多编码兜底解码，EXE 本身无缺陷 | 子进程冒烟记录 |
| 7 | deb 文档字符串仍写 v12.0 | 全量核对并更正版本口径 | `scripts/build_deb.py` |
| 8 | CI workflow 硬编码 13.0.0 版本 | 改为从 `core.config.APP_VERSION` 动态读取 | `.github/workflows/ci.yml` |

> 第 4、5、6 轮尤其重要：都是**「看起来像失败、其实是验证脚本自己写错」或「看起来通过、其实产物是假的」**。本版坚持用真实产物与真实子进程复验，不把脚本误判写成产品结论。

## 六、遗留事项（不阻塞本版）

1. v13.0 签名 APK 与真机验收，由 `build-android.yml` 在 tag 时完成。
2. GitHub 复审提出的 3 条低/中优先级建议（发布后 `gh release view` 校验、GUI exe 进 Release、detached HEAD 回写修复）。
3. 正式 `update.json` 需在 Release 资产齐备后由 `update-manifest.yml` 重跑生成；本地离线清单不作线上权威。
4. 公开分发前轮换 v11.5 快照中的 `starry-release.keystore`，或将该历史快照设为私有。
