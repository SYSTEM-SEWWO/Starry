# 资深程序员复审 · v12.0.0

**视角**：架构分层、依赖方向、测试可信度、状态与纯函数边界、可测试性、技术债。

---

## 1. 本轮最重要的判断：先修「测试的可信度」，再修功能

v11.5 的 `android/test_app_logic.py` 报「16/16 全绿」，但真机仍闪退。复审发现根因不在用例数量，而在**替身写反了**：

```python
# v11.5 的 fake 同时替换了 UI 和核心逻辑
class FakeMemory:
    def learn_from_conversation(self, prompt=None, answer=None):  # 复刻了错误签名
        pass
class FakeWidget:
    def scroll_to_bottom(self): pass        # 真实 Toga 0.5.7 根本没有这个方法
# Selection 不校验 value ∈ items               # 真实 Toga 会抛 ValueError
```

fake 是**照着被测代码写的**，于是把被测代码里的 F3 / F4 / F5 三个真机缺陷逐一抹平。
这是教科书式的「假绿」：测试通过率越高，越掩盖问题。

v12.0 的处理值得肯定，因为它改的是**测试原则**而不是补几个用例：

| 原则 | 落地 |
| --- | --- |
| 真实核心逻辑 | `tests/test_android_v12.py` 只 fake UI，`core` 全部用真实模块 |
| 替身必须忠实于第三方真实行为 | fake `Selection` 在 `value ∉ items` 时**主动抛 ValueError**；fake `ScrollContainer` **故意不提供** `scroll_to_bottom()`，`App.loop` 保持只读 property |
| 把历史 bug 固化成回归证据 | 专门有一条用例「旧的错误关键字调用确实会失败」，证明 F4 不是被绕过而是被修掉 |
| 旧测试不许继续造假 | 修正 `android/test_app_logic.py` 的签名、文本断言（递归收集 `children`）、`ActivityIndicator`，修正后 16/16 |

实测：`tests/test_android_v12.py` **37/37**、`tests/test_v12_features.py` **63/63**、
`android/test_app_logic.py` **16/16**、`check_core_parity.py` 全通过。

> 一句可复用的经验：**当替身是按被测代码而不是按真实依赖写的时候，测试只会证明代码和自己一致。**

### 1.1 收尾复核：另一个陷阱「隔离变量在目标平台上根本不生效」

本轮还纠正了一个延续多版的误判：`selftest.py` 首轮 761/12 被归因于
「运行环境依赖，CI 干净环境能过」。Chromium 内核装好后重跑，失败依旧（767/12）；
补 `USERPROFILE` 隔离降到 5 项，才定位到真正根因——
`core/gateway.py` 把统计 / 预算固定在 `~/.starry`，而 Windows 上
`os.path.expanduser("~")` 读的是 `USERPROFILE`，测试里 `HOME=tmp`
（乃至 `APPDATA` 隔离）对它**完全无效**，测试一直在读真实用户目录的累计数据。

修复没有去改测试的环境变量堆砌，而是给生产代码补了一个**显式的、
默认行为不变的契约**：`STARRY_DATA_DIR`（与 `STARRY_CONFIG_DIR` 同构），
自测各段注入各自独立的临时目录。这是更正确的分层——
**路径解析应当由被调用方声明，而不是由调用方猜平台的 `expanduser` 行为**。
同时不动默认路径，避免升级后用户统计「凭空消失」，也没引入数据迁移风险。

顺带修掉一个真实产品缺陷：`find_chromium()` 只找系统 Chrome，
`_on_web_install()` 没检查 Playwright **内置**内核是否已装好，
导致用户装完 118MB 内核后点按钮仍会重新下载。新增
`chromium_kernel_available()`（纯文件系统探测，不启动 driver、不与 Qt 事件循环冲突）。

结果：桌面全量自测 **779 通过 / 0 失败**，直接运行即可复现，
不再需要任何外部隔离变量。这一轮再次说明：**「看起来像环境问题的失败」
也要先证伪再下结论。**

## 2. 三端同源：把人工约定升级成机器门禁

v11.5 及之前靠「记得 `diff -q` 并手动复制」维持 `core/` 与 `android/core/` 一致，
资深程序员复审在 v11.5 的建议表里专门提过「CI 加字节一致门禁」，本轮落地：

```
core/                       唯一写入源
   │  scripts/sync_core.py（白名单排除 4 个桌面专属模块）
   ▼
android/core/               只读副本，禁止手改
   │  scripts/check_core_parity.py
   ▼
CI：版本单一真源（3 处）+ 41 文件字节一致 + 全量 AST 语法 → 通过才发版
```

- `VERSION_SOURCES` 把 `core/config.py::APP_VERSION`、`core/mcp.py::CLIENT_INFO`、
  `android/pyproject.toml::version` 三处声明绑定，`--expect-version` 再与 tag 对齐。
  这解决了「版本号改了两处忘了第三处」的老问题。
- 白名单 `DESKTOP_ONLY = {attachment, hotkey, models, workers}` 是**显式声明的例外**，
  比「同步后手动删掉」可靠得多；懒导出 `core/__init__.py` 再把安卓端缺失模块的
  裸 `ImportError` 包装成可读的 `AttributeError`。
- 实测 41 个文件一致、0 漂移。

依赖方向是**单向**的：`core/ → android/core/`。这个约束没有强制文件锁，
靠 CI 门禁 + 文档约定维持，属于可接受的轻量方案；若团队扩大，
可加 pre-commit hook 拒绝直接改 `android/core/`。

## 3. `core/stardust.py`：延续并强化了纯函数分层

延续 v11.5 `core/insights.py` 的分层思路，且约束更严：

| 约束 | 实现 |
| --- | --- |
| 零 GUI / 零网络 / 零第三方 | 只 `import hashlib, json, re`；AST 门禁扫描 |
| 不入参修改 | `messages` 转 list 后只算成本；`pack_archive` 用 `json.loads(json.dumps(...))` 深拷贝 |
| 确定性 | `ts` 等外部信息由调用方传入，函数内不读时钟、不读文件、不看全局状态 |
| 纯计划而非执行 | `plan_trim` 只返回 `keep_indices / drop_indices`，由调用方决定是否真的裁剪 |

**「返回计划而不是直接改数据」是本轮最干净的一个边界**：纯函数层不碰状态，
UI 层可以先给用户看「准备丢掉第 1、3 条」再执行；同一份计划也能被 CLI、
桌面、安卓三端复用而不需要三套实现。

存档用规范化 JSON（`sort_keys=True` + `separators`）计算 SHA-256，
这一点很关键：若直接对 `json.dumps(payload)` 求哈希，三端键顺序不同就会
互相拒绝导入。规范化序列化把跨端一致性做进了格式本身，而不是靠约定。

## 4. 配置层：「永不抛异常」是正确的取舍，但要付可观测性的账

`get_config_dir()` / `_safe_makedirs()` / `AppConfig.load()` 三层都改成绝不抛异常，
直接对应 F1 闪退。从架构上看这是把「fail-fast」换成了「degrade-gracefully」——
对一个安装在用户手机上、没有调试器的 GUI 应用，这个取舍是对的。

但代价必须记下来：`except Exception: pass` 会吞掉 JSON 损坏 / 权限错误，
用户可能静默以默认配置启动。v12.0 用「诊断」页 + `--doctor` + `crash_log`
补了可观测性，方向正确；**下版应把异常本体写进诊断日志**（目前只记条数与路径），
否则排查「为什么我的 Key 没了」仍然要靠猜。

`_safe_makedirs` 返回「最后一个候选路径」而不是 `None`，
保证调用方永远拿到一个字符串、不会出现 `TypeError`——这个细节处理得稳妥。

## 5. 构建与发版的工程化

| 脚本 / 工作流 | 复审评价 |
| --- | --- |
| `verify_apk.py` | 静态鉴定器本身也经历了 3 次自纠（Signing Block 头尾长度、dist-info 在 `app.imy` 内、AXML UTF-16LE 权限探测）。**工具自身的可信度被认真对待**，这点比多写几个 check 更重要 |
| `build_deb.py` | 纯标准库手搓 `ar` + `control.tar.gz` + `data.tar.gz`，绕开本机无 `dpkg-deb`；自带独立解析自检，不是「写完就说成功」 |
| `make_release.py` | 白名单 + `MANIFEST.md` + `checksums.txt` + `RELEASES.md` 索引；本轮安全复审又补了通配排除与 `assert_no_secrets` 发布前扫描 |
| `release.yml` | `verify → snapshot → publish` 三段式；依赖门禁与产物生成分离，失败定位清楚 |
| 三个 workflow | 共用 `concurrency: release-${{ github.ref }}`、`cancel-in-progress: false`，避免同 tag 并发互相覆盖 Release |

## 结论

**通过**。本轮最值得肯定的不是修了 8 个闪退缺陷，而是**先修了「为什么会误判修好了」**：
从「fake 核心」改成「真实核心 + 忠实替身」，把第三方库的真实行为
（`Selection` ValueError、无 `scroll_to_bottom`、`App.loop` 只读）写进测试。
配合三端同源门禁、版本单一真源、纯函数层边界与三段式发版流水线，
v12.0 把项目从「改代码」推进到「可验证地改代码」。技术债均已登记，不阻塞发布。
