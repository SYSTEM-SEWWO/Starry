# 资深程序员复审 · v13.0.0

**视角**：架构、并发模型、纯函数约束、失败模式、技术债　**结论：通过（2 条必改已修）**

---

## 1. 架构判断：分层是对的

```
core.project      只回答「做什么」：状态机 + 依赖 + 产物 + 存档     ← 零 I/O
core.parallel     只回答「怎么同时做」：分波调度 + 异常隔离 + 汇总   ← 零 I/O
core.updatecheck  只回答「有没有新版本」：版本 + 清单 + 资产校验     ← 除 load_manifest 外零 I/O
        ↓
core.cli          参数编排 + 打印（唯一允许联网的地方：_fetch_manifest）
ui/workbench_dialog  纯展示与交互（唯一允许弹文件框的地方）
```

**关键优点**：三层都不 import PyQt、不 import requests、不读全局配置。
这使它们能被 `tests/test_v13_features.py` 用真实对象直接测，也能被 PyInstaller
与 deb 两个完全不同的分发形态共用。与 v12 的 `core/stardust.py` 是同一套设计纪律。

## 2. 并发模型逐行复核

| 关注点 | 实现 | 评价 |
| --- | --- | --- |
| 结果顺序 | `results = [None] * len(jobs)`，用 `futs[future] = index` 回填 | **正确**。完成先后不影响输出顺序，`merge_results` 才能稳定生成表格 |
| 异常隔离 | `_call()` 内独立 try，`fut.result()` 外层再兜一层 | **正确**。双层保险，避免 worker 异常与 future 异常两种路径漏掉 |
| 超时 | `as_completed(futs, timeout=timeout)` 捕获 `FuturesTimeout`，`finally` 中 `shutdown(wait=False, cancel_futures=True)` | **正确**。这是本模块最要紧的一处：若用默认 `shutdown(wait=True)`，CLI 会在超时后继续卡住 |
| 超时后结果完整性 | `for i ... if results[i] is None` 补 「整体超时未返回」 | **正确**。报告长度恒定等于任务数，下游不必处理缺项 |
| 重试 | `attempts = retries + 1`，循环内吞异常，最后一次失败才返回错误 | **正确**，且重试在单线内，不占用其它线 |
| 循环依赖 | `guard < 100` + 剩余 pending 统一标 skipped | **正确**。不会死循环，也不会静默丢任务 |
| 依赖失败传播 | `ready_tasks()` 只认 `done`，上游 failed 时下游永不 ready → skipped | **正确**。语义清晰，且与 `project_progress.complete` 的判定一致 |

## 3. 纯函数约束复核

`core/project.py` 的所有变更函数（`add_task` / `update_task` / `run_project` 前的 clone）
都通过 `clone()`（`json.loads(json.dumps(...))`）先深拷贝再返回新对象，
不改入参。单测里有 4 条显式断言锁死这一点。
代价是 JSON 往返有性能开销，但项目规模是几十个任务，完全可接受，
换来的是可重放、可对比、可序列化——这个取舍是对的。

## 4. 本轮提出并已修复的问题

### P0-1　生成器按目录推断资产类型（已修）

初版 `platform_of()` 先按扩展名、再按目录名（含 `apk`）推断，
导致 `releases/assets/v13.0.0/apk/README.md` 被判为 android 资产，
`update.json` 里出现一个 `name: README.md` 的「APK」。
`validate_manifest()` 是结构校验，会认为它完全合法——**这是最危险的那种 bug：
校验全绿，但产物是假的**。

修复：只按二进制扩展名判定，目录名不再参与；补 10 条单测，包括
「apk/README.md 不是资产」「空目录拒绝生成」「哈希来自真实字节」。
**判断依据**：宁可少收录资产，也不能编造资产。

### P0-2　测试与发版号耦合（已修）

v13 单测把 `13.0.0` 同时当作「当前版本」和「远端新版本」，
版本真源升级后 3 条用例立刻失效。修复为 `REMOTE_VERSION = "99.0.0"`，
并把 v12 测试里的硬编码版本断言改成动态读取 `cfg_mod.APP_VERSION` /
直读 `core/config.py`。**判断依据**：测试应验证「关系」，不应复述「常量」。

### P1（不阻塞，登记）

1. `local_worker` 的 `check` 类型把「文本为空」编码为 `passed: False` 但仍返回成功，
   上游 `run_parallel` 记 `ok=True`。这是有意的（校验结果也是结果），但 API 文档必须写清，避免调用方误读。
2. `--execute` 目前只让 `chat` 类任务走真实模型，默认模板的三条并行线仍是本地确定性执行。
   若未来要「真正多模型并行」，需要在 CLI 层把 `kind` 与模型路由显式绑定。
3. 工作台在 GUI 线程同步执行并行。当前 worker 是毫秒级，没问题；
   若接入真实模型 worker，必须换 `QThread` + 信号，否则界面会冻结。

## 5. 与 v12 修复的一致性

v12 收尾时定位并修掉过一个「隔离变量在目标平台根本不生效」的陷阱
（`HOME` 在 Windows 不控制 `expanduser("~")`，改用显式 `STARRY_DATA_DIR` 契约）。
v13 延续了这个教训：**不使用隐式环境约定**。
`STARRY_UPDATE_URL` 是显式契约，未配置就明确报「离线模式、未发起任何网络请求」，
而不是悄悄尝试某个默认 URL。这点值得保持。

## 6. 结论

**通过**。并发、序列化、失败模式都经得住逐行复核；
两条 P0 已在本版内闭环并补了回归测试；P1 三条已登记，不影响发布。
