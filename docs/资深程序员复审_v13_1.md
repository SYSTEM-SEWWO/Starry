# 资深程序员复审 · v13.1.0

> 关注点：并发与状态、纯函数约束、id 稳定性、失败模式、以及「测试绿但产物假」。
> 本轮不靠通读印象下结论，每条缺陷都有可复跑的最小复现与修复后的断言。

## 1. 本轮定位并修复的真实缺陷（5 项）

| # | 缺陷 | 真实后果 | 修复 |
| --- | --- | --- | --- |
| P1 | `_scalar()` 把 `allowed-tools: Read, Bash, Grep` 当普通字符串 | 统一模型里 `tools` 时而字符串、时而列表，上层无法稳定消费 | 引入 `_LIST_KEYS`，在 `parse_frontmatter` 出口统一 `_as_list()` 归一化；`_as_list` 幂等 |
| P2 | `parse_hub_entry()` 用 `remote:` 前缀**重造** id | 本地 `github:x` 与远端 `remote:github-x` 对不上，`diff_skills()` 把每个技能同时判成 `added` + `removed` | 条目已带 `id`（含 `:`）时原样沿用；否则用条目 `source` 拼装 |
| P3 | `check_hub_update()` 用 `_skill()` **重算**的 sha256 比对 | 清单只带元数据、正文为空，重算值必然与本地不同 → 每个技能都被误判 `changed` | 比对改以清单**声明**的 `sha256` 为准（`declared` 覆盖顶层），缺失才回退 SemVer |
| P4 | 扁平 `*.skill.md` 把文件名作为 `name` 参数传入且优先级最高 | 覆盖 frontmatter 里更权威的 `name`，同一技能在清单与本地得到不同 id | 优先级改为 `meta.name → name 参数 → 目录名 → "skill"` |
| P5 | `_as_list()` 对 dict 输入做 `str(dict).split(",")` | 畸形嵌套字段产生垃圾条目 | dict 直接返回 `[]` |

这 5 项里有 3 项（P2/P3/P4）属于**同一类根因：标识与内容的不一致**。
只做「能解析」的冒烟会发现不了它们，必须做「本地 → 导出清单 → 再比对」的往返测试。
因此 `tests/test_v13_1_hub.py` 专门锁死了往返一致性：
`check_hub_update(found, build_hub_manifest(found))` 必须 `update_available=False`。

## 2. 测试质量本身的问题（2 项）

- **假绿**：`CLI --hub-manifest 缺文件时安全退出` 在参数尚未接入时，
  argparse 抛 `SystemExit(2)` 也会让断言 `rc != 0` 通过。这不是「缺文件被拒绝」，
  而是「参数不认识」。修复：接入后手动复跑，确认输出是
  `读取 Hub 清单失败：…（文件不存在或不是合法 JSON）` 且 RC=2；
  并给 `cli_run()` 加 `SystemExit` 收敛，保证测试跑完整而不是中途崩掉。
- **断言过松**：原先用 `"hub" in spec.lower()` 判断 GUI spec 是否接入，
  只要文件里任意位置出现 hub 字样就通过。已收紧为逐项精确匹配
  `"core.hub"`、`("skills", "skills")`、`"ui.hub_dialog"`、
  `"ui.workbench_dialog"`，并增加 `smoke_gui_exe.py` 与 workflow 的存在性检查。

## 3. 架构复核

| 检查 | 结论 |
| --- | --- |
| `core/hub.py` 是否零 GUI / 零第三方依赖 | 是。只 import `hashlib/json/os/re` 与同层 `core.updatecheck`，可随 Android 同源分发 |
| 是否修改入参 | 否。`_skill()` / `build_hub_manifest()` / `diff_skills()` 均返回新对象；`Hub.discover()` 返回 `list()` 副本 |
| 缓存一致性 | `add_source` / `add_starry` / `_refresh` 都会置 `_skills=None` 或 `refresh=True`；GUI 导入后调 `_refresh()` |
| 失败是否抛到启动流程 | 否。`scan_dir` 对 `OSError/UnicodeError` 逐文件跳过；`check_hub_update` 纯逻辑返回结构化结论；`validate_hub_manifest` 返回 `(ok, reason)` |
| 三端同源 | `scripts/sync_core.py` 同步 45 个文件；`--expect-version 13.1.0` 门禁通过，桌面专属 4 个白名单不变 |
| 懒加载 | `core/__init__.py` 加 `"hub": "core.hub"`，`import core` 不会因此拉起额外依赖 |

## 4. 遗留的 P0-2 闭环

v13.0 复审登记「测试与发版号耦合」为遗留项：`tests/test_v13_features.py`
硬编码 `APP_VERSION == "13.0.0"`，每次升版都要手改。本版改为
**SemVer 下限断言**（`_ver_tuple(APP_VERSION) >= (13, 0, 0)` 且三段），
并把生成器自测里的 `"13.0.0"` 改为动态读取 `cfg_mod.APP_VERSION`。
`release.yml` 的生成器自测也改为从 `steps.ver.outputs.version` 注入环境变量。
至此该 P0 项关闭。

## 5. 仍需注意的取舍

1. **frontmatter 解析器是有意限定的子集**，不是通用 YAML。
   不支持锚点、多行列表嵌套、复杂类型。对 Skills 规范足够，且换来零依赖与三端一致；
   遇到不支持的写法会退化为字符串，不会抛异常，但工具/标签可能为空——
   这是可接受的降级，不值得为此引入 PyYAML。
2. **`--hub-import` 复用 `SkillManager.add_custom`**，同 id 覆盖更新。
   这意味着从 Hub 重新导入会覆盖用户手工编辑过的同名技能，属于预期行为，
   已在 CLI 输出与文档中说明。
3. **GUI EXE 自检依赖落盘文件**：`--out` 目录不可写时，自检仍会计算完成但
   冒烟脚本读不到结果而判失败。这是**故意的保守**——宁可报错也不误判成功。
