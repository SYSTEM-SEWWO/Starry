`core/mcp.py` 的全部外部导入：`json / os / queue / re / subprocess /

协议最稳定的一小部分（`initialize` / `tools/list` / `tools/call`），
约 200 行有效代码换来了**零新依赖**。

## 四、坦白清单（不遮掩的已知边界）

1. **只支持 stdio 传输。**
   MCP 另有 HTTP/SSE（streamable HTTP）传输形态；本轮未实现。若用户配置了
   HTTP 型服务器，会握手失败并给出可读错误，不会静默卡死。

2. **工具名做了有损折叠。**
   OpenAI 的 function name 只允许 `[A-Za-z0-9_-]`。中文服务器名/工具名会被
   折叠为下划线（如 `本地文件` + `read_file` → `mcp_read_file`）。
   极端情况下两个不同的中文名可能折叠成同一个 id——发生概率低（MCP 服务器名
   通常为英文），但属于已知边界，未做冲突检测。

3. **「测试连接」是同步的，最长 8 秒。**
   设置页点击后会阻塞 UI 最多 8s。启动路径已改为后台线程（不阻塞），
   但手动测试为简化未再套线程——下轮可改为异步。

4. **抓屏在部分 Linux 会话下可能受限。**
   `QApplication.primaryScreen().grabWindow(0)` 在 Wayland 的部分合成器上
   可能返回空图；代码已做 `isNull()` 保护并提示"未能捕获屏幕画面"，
   不会崩溃，但功能不可用。

5. **MCP 工具没有护栏。**
   外部 MCP 服务器完全可能提供"写文件/执行命令"类工具，本轮注册后
   智能体可直接调用，尚无确认环节。这是**下轮最高优先级**：接入即意味着
   攻击面扩大，必须补动作确认（Jini 的 YES/NO 卡是成熟参照）。

## 六、给 HR 复审的结论建议

1. 本轮是**"先检索、再取舍、后落地"**的完整闭环：有外部证据（GitHub 检索）、
   有明确的不做清单、有可核对的增量与自测数据。
2. 工程上的关键判断是**用 200 行标准库代码替代一整套异步 SDK**，
   把依赖树增长控制为零——这体现的是成本控制意识，不是"能跑就行"。
3. 需要 HR 注意的是第 5 条坦白：MCP 接入把工具供给变成变量的同时，
   也把安全风险变成变量。建议下一轮把"动作确认护栏"列为**必办项**而非优化项。
